# 3D NPC 集群寻路：方案设计与实现

> 目标：点击地图上一点，100+ 个 NPC 从不同起点集体移动到目标区域。地形有上下坡；单位不重叠、不被平移推挤、被挡时自己让路、全程平滑，并且全部到达。
> 交付物是可脱离 Unity 运行和验收的 C# 核心（`netstandard2.1`），不是一段只写在纸上的方案。

---

## 1. 结论

采用 **高度场导航网格 + 每单位 A*（时间分片） + 视线拉直 + ORCA 局部避让 + 六边形目标车位（保持队伍相对队形） + 顺序安全提交 + 主动让路/落点压实** 的混合方案。

选择它而不是直接使用 `UnityEngine.AI.NavMeshAgent`，原因是 RTS 群体移动的难点不在“找一条路”，而在：

- 100+ 个单位同时走同一条路时的**交通流**；
- 单位之间的**不重叠**和**不互相平移**；
- 点击点物理容量有限时，怎样定义“到达”；
- 最后一公里（目标落点）的拥堵和让路；
- 移动端每帧预算。

Unity 自带寻路可以解决“从 A 到 B 的静态路径”，但其局部避让是黑盒的，容易出现推挤、滑动、绕圈和穿透；对“绝不重叠 / 绝不平移”这种硬约束不够可控。因此本方案把问题拆成三层，分别用可控的算法解决。

## 2. 需求拆解

| 需求 | 技术问题 | 本方案的对应机制 |
|---|---|---|
| 地形有斜坡上下起伏 | 2D 网格不能直接表示高度 | 高度场；每个格子带高度；A* 边带坡度代价；单位 Y 取地形采样 |
| 单位不能重叠 | 局部避让不能只靠力 | 水平胶囊 + 每 tick 扫掠线段检查 + 提交后二次校验；最小间距硬约束 |
| 不能把别人平移挤开 | 物理推挤会产生“被平移” | 从不修改其他单位位置；单位只改自己的速度；没有冲量/位置修正 |
| 挤兑时被挤者自己走开 | 需要让路状态机 | 已到达单位检测到自己挡住别人时，自己走到临时空位，3 s 后回来；迟到增援整队重新排位 |
| 目标被占满，后来者仍要接近 | 单点目标容量无限大是伪命题 | 把目标点扩展成按人数计算的落点区域；软车位 + 压实 |
| 全程平滑，不抖动/瞬移 | 速度不连续、离散候选方向会抖 | ORCA 连续速度、加速度上限、固定 60 Hz、路径视线平滑、到点后速度归零 |
| 全部到达，不跟丢/不提前停 | 局部死锁、路径失效 | 卡住重规划、目标区域完成判定、逐单位断言 |
| 100+ 单位不卡 | 每单位 A* 与邻居查询开销 | 邻居空间哈希、每 tick 只规划 2 条路径、无每帧堆分配、线性规划小规模 |

### 2.1 最关键的设计取舍：目标点不是“一个点”

半径 0.35 m 的胶囊，120 个的截面积约：

```
120 × π × 0.35² ≈ 46.2 m²
```

即使按接近六角密排的 70% 效率算，也需要约 **66 m²** 的可用地面；这还没有算单位之间的安全间距和地形边界。把它们全部塞进一个数学点，在“不重叠”的前提下是不可能的。因此：

- 点击的 `(x,z)` 是**目标区域中心**；
- 系统按人数生成六边形排列的**软车位**，并按队伍相对队形分配；
- 单位在目标区域内就近压实；
- “全部到达”定义为：所有单位进入由人数决定的落点区域，且不再移动；
- 若业务要求“每个人都精确踩到某个车位”，需要用全局调度和空位缓冲区做重排；本项目不把它作为默认行为，因为它会显著增加抖动和卡顿风险。

这个定义在 RTS 里是常见的：玩家点一个位置，部队在周围展开，而不是全部叠在一个像素上。

## 3. 行业方案对比

| 方案 | 优点 | 局限 | 适用 |
|---|---|---|---|
| Unity `NavMeshAgent` + 内置 avoidance | 接入快，支持 NavMesh、OffMeshLink、斜坡 | 避让质量黑盒；100+ 时推挤/绕圈/穿插；不保证不重叠；目标落点语义弱 | 少量单位、快速原型 |
| Recast/Detour + DetourCrowd | 工业级 NavMesh、路径走廊、局部避让、成熟 | C++/插件接入；默认避让仍可能互相推挤；目标车位/让路要自己加 | 大型地图、生产级 |
| A* Pathfinding Project | Unity 生态成熟，Grid/Graph 多 | 仍是“寻路 + 可选避让”；群体硬约束需扩展 | Unity 独立项目 |
| Flow Field | 同一目标下每单位极便宜，RTS 常用 | 多目标/多队伍要多张场；终点精确站位弱；局部拥堵需额外处理 | 大量单位、同一目的地 |
| Potential Field / Boids | 简单、平滑、便宜 | 局部极小、死锁、无法保证不重叠 | 装饰性群体、鱼群 |
| RVO2 / ORCA | 互惠避让、连续速度、工业验证充分 | 只解决局部；目标拥堵/静态障碍仍需外层；极端密度会死锁 | 人群、RTS 局部避让 |
| **本方案：Grid A* + ORCA + 车位/压实** | 可控、可测、无 Unity 依赖、100–300 单位性能好 | 路径层是栅格，超大世界需换 Recast；精确车位非硬保证 | 本次需求、Unity 手游原型 |

**为什么不用纯 Flow Field？** 单目标、同队伍时它确实更快；但本项目需要每个单位有独立终点（软车位）、需要卡住重规划、需要让路状态机。用 A* 可以更直接地得到“这个单位去哪个车位”的路径，且 100–300 单位的时间分片 A* 已足够快。若以后同屏 1000+ 且全部去同一点，建议把路径层换成 Flow Field 或 DetourCrowd。

**为什么不用纯 ORCA？** ORCA 只回答“下一帧速度是多少”，不回答“目标区域满了怎么办”“被挡住的人怎么让”“谁先到”。本项目的顺序提交、软车位、让路和压实才是满足需求的关键。

## 4. 地形与路径层

### 4.1 高度场

`HeightMap` 保存规则网格的高度，格心高度，双线性采样：

```
world (x,z) -> grid (gx,gz) -> 四个格心高度 -> 双线性插值
```

`NavGrid` 在此基础上烘焙：

- **坡度可走性**：中心差分估计坡度，超过 `maxSlope`（默认 42°）的格子标记为不可走；
- **静态障碍**：圆形岩体标记为不可走；
- **净空**：对不可走格做欧氏距离变换，得到每个格心的净空；再要求 `净空 >= 半径 + 余量 + 半格`，避免贴边；
- **连续净空**：`IsWorldWalkable` 不是只查“当前格是否可走”，而是做**圆 vs 格子矩形**的精确相交检查。只在格子级别检查会出现“圆心在可走格边界、身体已经插进旁边不可走格”的经典陷阱；
- **扫掠净空**：`IsSegmentWalkable` 对路径线段与障碍格矩形做扫掠相交，并检查坡度连续性，避免切角。

> 实现位置：`src/CrowdNav/NavGrid.cs`、`HeightMap.cs`。

### 4.2 A*

- 8 邻接；
- 禁止从两个阻挡格之间斜穿；
- 步长代价 = 水平距离 × 坡度惩罚 + 上坡惩罚；
- 启发式用欧氏距离，可采纳；
- 一次点击为每个单位规划一次；卡住时重规划。

路径是格子中心序列，直接跟随会出现锯齿。`PathSmoother` 做**有界视线拉直**：从当前位置向后找最远的、整段可走的节点，只保留长弦。这样既去掉网格锯齿，又不会为了“最优”而做很重的漏斗算法。

### 4.3 时间分片，避免点击卡顿

100 个单位 × 单次 A* 约 0.5–0.6 ms，一次性规划约 70 ms，在手游上是一个明显卡顿。实现改为：

- 命令下达时只建目标布局、分配车位，把路径请求按“离目标近的优先”入队；
- 每个 tick 处理 `PathPlanFrameBudget` 条（默认 **2**）；
- 先规划的单位先走，后面的单位在 1 秒内陆续启动，视觉上像部队依次出发；
- 测得的规划峰值帧耗时约 4.5 ms（含首次 JIT），稳态不规划时 p95 小于 1 ms。

> 实现位置：`CrowdSimulation.QueueAllPathPlans()`、`ProcessPathQueue()`。

### 4.4 为什么会出现“倒回去跑”，以及修复

第一版轨迹里确实有单位跑出 10–30 m 的回头路。用轨迹分析定位到根因，不是绕障，而是**路径点推进条件太窄**：

- 路径经过视线拉直后只剩几个长弦路点；
- 局部避让从侧面挤了单位 1–2 m，它从路点旁边“擦过去”，没有进入 0.38 m 的到点半径；
- 旧逻辑只有在距离路点 1.0 m 内且速度背离时才前进，于是路点留在身后；
- 人群交通推着它继续向前，等拥堵缓解，它再回头去追那个旧路点，追到后才继续下一个。视觉上就是几十米的逆向跑。

修复（`CrowdSimulation.AdvanceWaypoints`）：

1. 如果已经越过当前路点的垂面，且到下一个路点视线可达，就跳过旧路点；
2. 如果在 2.8 m 内已经背离当前路点，且下一个路点可达，也跳过；
3. 不满足视线条件时仍然老实回到路点，避免为了省路而穿岩体；
4. 最终车位仍要求精确接近，最后一段不做大范围跳点。

修完后 120 人从 56.1 s 降到 38.2 s，但 300 人还有单位会倒跑约 10 m。继续定位发现第二类问题：

- 单位被挤到路点侧后方，下一段路径的直线被岩体挡住，不能安全跳过；
- 它没有卡住（仍在高速移动），旧的“卡住才重规划”不会触发；
- 于是它沿着旧路径**走回**上一个路点，再绕岩体前进，表现为 10 m 级回头路。

修复（`AdvanceWaypoints` + `RequestReplan`）：如果目标路点在身后、不能安全跳点，且单位已经明显偏离路径，就直接从当前位置重规划，而不是走回去。目标区内部不做这种重规划，避免目标区拥堵时来回重算。

第三类问题不是局部避让，而是**车位分配把队形打乱了**：旧逻辑按“到目标的距离 + 圆环角度”分配车位。300 人全从西侧来时，后排单位可能抽到圆环东/北侧的车位，于是它先接近目标圈，再沿圈外绕到自己的远侧车位；看起来就是“已经进圈又跑出去”。

修复不是改目标形状，而是**保持队伍相对队形**：

- 记录每个单位相对队伍质心的偏移；
- 把偏移整体平移到目标圆心，得到它的理想车位；
- 再用两两交换把“理想车位 → 实际车位”的总距离压到最小；
- 整圆仍然是整圆，点击点仍然是圆心；只是后排单位不会再被硬塞到圆环远侧。

300 人整圆测试里，没有单位跑到目标圈外；最大单步径向回退约 0.12 m，属于人群避让的弧线，不再是“目标路点留在身后”造成的整段倒跑。整队完成 30.3 s，最终仍填满整个圆。

## 5. 目标落点层

### 5.1 六边形软车位

`GoalLayout` 从目标中心向外生成六边形环：

- 环 0：中心；
- 环 k：6k 个点；
- 间距默认 1.0 m（单位直径 0.7 m + 0.3 m 余量）；
- 过滤不可走 / 净空不足的点；
- 每人一个唯一车位，作为“软目标”。

### 5.1.1 为什么不能按圆环角度硬分车位

旧分配方式假设“离目标近的人拿内圈、同一圈的人按角度匹配”。这只在队伍从四面八方包围目标时成立；如果 300 人全从西侧来，圆环东/北侧的车位对任何单位都很远，分到谁，谁就得绕过整个人群。

现在保留整圆车位，但分配改成**队形保持**：

- 先算队伍质心；
- 每个单位的相对偏移平移到目标圆心，得到“它本来应该在的位置”；
- 选最近的空闲车位，再做若干轮两两交换，降低总位移；
- 前后排关系保持不变，整支队伍像一块软体一样平移过去；
- 单位不需要为了填满圆环而交换到远侧。

因此目标区仍是整圆，最终也会被填满；被取消的是“远侧固定车位预留”这个导致绕圈的约束。需要回到旧的按环分配时，把 `FormationPreservingAssignment` 设为 `false`。

车位不是“硬终点”。它解决的是“所有人朝同一个点挤”的问题：每个单位有明确的减速/停靠位置，路径不会全部汇聚到同一个格。

### 5.2 分配

- 按单位当前离目标的距离排序，内圈给先到的单位；
- 同一环内按极角排序，并尝试旋转对齐，减少交叉；
- 车位固定后，每个单位只走自己的路径。

### 5.3 目标区域压实

虽然每人有车位，但在高密度和“不推挤”约束下，要求 120 人全部精确站进各自车位，等价于一个带空位缓冲的滑动拼图；局部避让不保证能完成，且会导致长时间来回挪动。

因此实现一个**容量感知的完成判定**：

- 目标区域半径 = 最外圈车位半径 + `GoalFootprintPadding`（默认 1.0 m）；
- 当所有单位都进入该区域，并且连续 `GoalSettleDwell`（默认 4 s）没有新的单位进入，认为整队已在目标区域压实；
- 把所有单位标记为 `Arrived`，速度清零；
- 测试仍逐单位检查：必须进入区域、必须没有重叠、必须没有瞬移；
- 300 人测试还额外断言：进入区域后不得跑到半径 +1 m 外，防止“进圈又跑出去”；
- 车位误差单独统计，不作为“是否到达”的唯一标准。

这是对“点击一个点”的工程化解释：点变成容量足够的区域，所有人到达区域，而不是要求所有胶囊共享一个坐标。

### 5.4 主动让路（要求 3）

`UpdateCourtesyYields` 的逻辑：

1. 一个仍在移动的单位被堵住超过 0.65 s；
2. 它在目标区域附近；
3. 从它到目标车位的线段上，找一个已经到达的阻挡者；
4. 阻挡者自己选一个 1.0–1.9 m 外的、可走、与其他单位不重叠、且不挡目标线的临时点；
5. 以 0.42 倍速度走过去，待 3 s；
6. 回到自己的车位。

阻挡者是**自己走开**的，不是被推开的。单位之间没有位置修正。

### 5.5 迟到增援（要求 3 的强化版）

如果整队已经压实完成，又追加单位：

- 重新生成更大的目标布局；
- **所有单位重新分配车位**；
- 已到达单位被重置为 Moving，走回自己的新车位；
- 新单位从出生点走向外圈；
- 这就是“前面的单位慢慢挪动腾出空间，让后面的单位接近”的可见版本。

测试 `late_reinforcement` 验证了 `ReflowCount > 0`，且最终 140/140 到达。

## 6. 局部避让与不重叠

### 6.1 ORCA

`OrcaSolver` 使用 RVO2/ORCA 的经典做法：

- 对每个邻居构造速度空间中的半平面；
- 用线性规划求“最接近期望速度、同时满足半平面”的速度；
- 每个邻居只承担一半的避让责任（互惠）；
- 时间视野默认 1.5 s；
- 额外安全半径 0.10 m。

我们在 RVO2-CS 的线性规划实现上做了适配（Apache-2.0，版权头保留在文件顶部），外层交通流、顺序提交、目标车位和让路逻辑为本项目实现。

### 6.2 速度平滑

- 期望速度来自路径跟随，接近目标时按距离减速；
- ORCA 输出经过加速度限制（默认 15 m/s²；刹车 1.8 倍）；
- 朝向只用于渲染，不参与运动约束。

### 6.3 顺序安全提交（硬约束）

这是“绝不重叠”的最终保险。每个 tick：

1. 所有单位先算出自己的 ORCA 速度；
2. 按“离目标车位近的优先”排序；
3. 依次尝试移动；
4. 如果整步会穿过静态障碍或任何尚未移动单位的当前位置（已移动单位用新位置），则二分缩小步长，直到安全；
5. 单位自己的位置只由自己的步长改变；**没有“把别人推开”的代码路径**；
6. 所有单位提交后，再检查一次两两间距；默认顺序模式下不会出现残余重叠；若出现，只取消自己这一步，不会平移别人。

为什么“离目标近的优先”？它让前排先走，后排再跟进，形成类似队列的交通流；如果反过来，后排先动会顶住前排，容易死锁。

### 6.4 为什么能做到不重叠

- 初始位置检查，若重叠直接抛异常，不进入“带病运行”；
- 每次移动检查的是**扫掠线段**，不是只检查终点；
- 提交后再做一次全局间距校验；
- 单位半径固定，最小间距 0.72 m；
- 测试逐 tick 计算所有单位对的距离，记录最小值和重叠帧数。

### 6.5 为什么没有“被平移”

代码中没有：

- `position += push`；
- 刚体冲量；
- `NavMeshAgent` 的自动避让位移；
- 把重叠单位推开的位置修正。

只有一个例外：`ResolveResidualOverlaps` 在极端情况下会**取消某个单位自己本 tick 的移动**（把位置减回自己的旧位置），这不是另一个单位推它，而是它自己的安全回退。默认的顺序提交模式下不会触发；保留它是为了让“同时提交”实验模式也有硬保证。

## 7. 性能

### 7.1 关键手段

- **邻居空间哈希**：每 tick 重建一次，查询 1.25 m 格子；
- **每单位最多 12 个邻居**；
- **ORCA 线性规划**只有十几条半平面，计算量小；
- **每 tick 只规划 2 条路径**，避免 100 次 A* 的点击尖峰；
- **无每帧堆分配**：路径、邻居、提交缓冲、ORCA 线都复用；路径只在命令/重规划时分配；
- **无 Unity 依赖**：核心是纯 C#，方便 IL2CPP。

### 7.2 实测

环境：Intel Core i7-14700F，.NET 10，Release。移动端会慢 2–4 倍，实际以目标机 Profiler 为准。

| 场景 | 单位 | 全部到达 | 规划总耗时 | 规划峰值帧 | 稳态帧 p95 | 稳态帧 max | 最小间距 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 起伏地形 | 120 | 26.8 s | 84.9 ms / 60 帧 | 5.4 ms | 0.467 ms | 1.94 ms | 0.720 m |
| 目标区压力 | 160 | 12.4 s | 21.8 ms / 80 帧 | 2.7 ms | 0.388 ms | 6.57 ms | 0.720 m |
| 平地 | 200 | 15.7 s | 2.4 ms / 100 帧 | 0.1 ms | 0.521 ms | 0.89 ms | 0.785 m |
| 起伏地形 | 300 | 30.3 s | 144.7 ms / 150 帧 | 1.7 ms | 1.284 ms | 2.13 ms | 0.720 m |
| 迟到增援 | 140 | 84.0 s | 71.1 ms / 115 帧 | 1.5 ms | 0.199 ms | 1.63 ms | 0.720 m |

说明：

- “规划总耗时”是时间分片累计的 CPU 时间，不是单帧；
- 起伏地形 120 的一次约 1.9 ms 稳态峰值来自运行中的重规划/GC；目标区压力场景的一次 6.6 ms 峰值来自目标区一次性压实；p95 仍分别约 0.47 / 0.39 ms；
- 输出里的 `maxAccel` 偶尔接近 186 m/s²，来自极少数“硬安全检查直接取消本 tick 移动”和一次性整队压实；`accelP99` 约 27 m/s²，到达后残余移动为 0。若业务要求连一次硬停都不能有，可提前减速（增大 ORCA margin / 降低最大速度），代价是通过性下降；
- 起伏地形的完成时间包含长距离、山脊/岩体绕行和目标区压实；
- 300 人时稳态 p95 约 1.28 ms，仍在一个 60 fps 帧预算内；真正的瓶颈会从局部避让转向路径规划和渲染；
- 移动端建议 `PathPlanFrameBudget=1`、`MaxNeighbors=8`、`NeighborDistance=1.6`，并把渲染与仿真解耦。

### 7.3 规模再往上

- 同屏 500–1000：把 A* 换成 Flow Field 或 Recast/Detour，局部避让保留；
- 多队伍/多目标：每队一张流场，ORCA 只做局部；
- 需要大量动画：把 `Agent` 改成 struct + SoA，或使用 Unity DOTS/Jobs 并行 ORCA；
- 大地图：分块导航网格 + 层次 A*。

### 8.2.1 FBX 导入流程

`neicheng_walk01.fbx` 是 ASCII FBX，包含 168 个顶点、128 个三角面，所有三角面法线朝上，
同一 x/z 位置没有上下重叠层，因此可以无损转成规则高度场：

1. 解析 `Vertices` / `PolygonVertexIndex`；
2. 检查法线/重叠，确认是单层可行走表面；
3. 以 0.8 m 网格、4 m 边距光栅化；**X/Y/Z 统一缩放 5 倍**，否则水平放大 3 倍而高度不放大，
   台阶会被视觉压扁；
4. 输出 `heights[]`、`walkable[]` 和**原始三角面** `mesh.vertices/indices` 到
   `src/CrowdSim.Interactive/Maps/neicheng_walk01.json`；
5. `MapCatalog` 加载为 `HeightMap + NavGrid`，与程序化地图共用同一套 A*/ORCA/车位逻辑；
6. 3D/2D 显示直接用原始三角面，高度场只用于 AI 净空/碰撞，避免 0.8 m 栅格造成边缘凹陷。

导入图目前是**单层表面**；桥、洞、上下层需要多层导航结构，不能压成单张高度场。

导入图在 3× 水平缩放下，平台到中央低区的窄口只有约 1.2 m，300 人会堵死；改为统一 5× 后
窄口约 2 m，300 人从平台穿过窄口到中央低区 42.0 s 全部到达。高度与水平尺寸保持同一比例，
不会再出现“高度被压低”的视觉。

如果目标点本身落在细长通道里，普通圆环车位仍会让前排停在通道中间。`QueueNarrowGoal` 会检测
目标格净空；窄通道内同样把点击点作为最终目标，单位沿 A* 路径排队通过，不再被分配回
出生区的队列车位。开阔目标下所有单位直接朝点击点走，不再停在外圈车位。
目标点 UI 只显示小标记，不再显示会随人数扩大的容量圆；开放目标内部半径 120 人约 6.4 m、
300 人约 10 m，但不再画大圆。容量只参与内部车位/完成判定。

`GoalCenterAttraction` 在开阔目标下会让已进入目标区域的单位把目标改为点击点本身，而不是
停在外圈预留车位；只要还有安全空间就继续向里靠，真正挤满后才停。窄通道同样以点击点为
目标，但先做容量检查；装不下就报错，避免把车位铺回出生点导致“原地到达、四处散布”。

单位参数通过 `SetUnitConfig` 重建 `NavGrid`、碰撞半径、车位间距和出生队形；
客户端按 `unitScale` 放大胶囊和阴影。移动速度改 `MaxSpeed`，与 1×/2×/4× 播放倍速相互独立。

启动：双击 [`run-interactive.cmd`](../run-interactive.cmd)，或：

```powershell
dotnet run --project src/CrowdSim.Interactive/CrowdSim.Interactive.csproj -c Release --no-launch-profile
```

打开 <http://127.0.0.1:8799/>。当前会话中该服务已在运行。

## 9. Unity 接入

详见 [Unity 接入指南](Unity接入指南.md)。核心步骤：

1. 把 `src/CrowdNav/*.cs` 拷入 `Assets/CrowdNav/`；
2. 用 `Terrain.SampleHeight` 或射线构建 `HeightMap`；
3. 用 `CircleObstacle` 标记岩体；
4. 创建 `NavGrid` / `SimulationConfig` / `CrowdSimulation`；
5. 点击地面 → `SetGoal(new Vec2(hit.x, hit.z))`；
6. `Update` 里固定步长 `Step(1/60)`；
7. 把 `Agent.Position` + 地形高度写到 `Transform`。

不需要 Unity NavMesh。若你更希望用 NavMesh 做路径，也可以只复用本项目的目标车位、ORCA 和顺序提交层。

## 10. 局限与边界

1. **精确车位不是硬保证**。密集时允许在目标区域内压实；如果业务必须精确站车位，需要全局重排调度。
2. **水平胶囊**。没有跳跃、攀爬、飞行；陡坡直接不可走。
3. **静态障碍仅圆形 + 坡度**。动态障碍、门、电梯需要额外层。
4. **极端几何会死锁**。狭窄死胡同、大量单位同时反向，任何纯局部方法都可能死锁；需要全局交通管制。
5. **路径规划是栅格 A***。超大地图应换 Recast/Detour，或用流场。
6. **Unity 示例未编译**。核心库已测试；`Unity/CrowdRunner.cs` 是接入样板，需要按项目调整地形、预制体和图层。
7. **“全部到达”= 到达目标区域**，不是所有人同一坐标。这是本方案最重要的语义约定。
